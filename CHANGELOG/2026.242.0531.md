# 2026.242.0531 — fix: stamp the root manifest at the schema this repo's CI charly supports

## Summary

Repairs a regression I introduced in the previous PR.

The root `charly.yml` I added stamped schema **`2026.240.1943`** (the current HEAD), but
this repo's `deploy.yml` pins charly **`v2026.238.1242`**, whose maximum supported schema is
**`2026.232.0520`**. So the `candy` workflow started failing on `main`:

```
config schema 2026.240.1943 is newer than this charly supports (max 2026.232.0520)
```

This stamps `2026.232.0520` — the value the 226 peer candy repos already carry, and the one
this repo's pinned charly accepts.

Nothing else changes: the candy files under `candy/` are untouched, because the schema
requirement applies to the project **root** manifest only.

Refs opencharly/charly#459.

## How tested

Against a binary built from **this repo's exact pinned charly tag** (`v2026.238.1242`), not
a newer local build — that mismatch is what caused the regression:

```
$ charly box validate     # root stamped 2026.232.0520
exit=0                    # accepted

$ charly box validate     # root stamped 2026.232.0521
config schema 2026.232.0521 is newer than this charly supports (max 2026.232.0520)

$ charly box validate     # root stamped 2026.240.1943  (what the previous PR shipped)
config schema 2026.240.1943 is newer than this charly supports (max 2026.232.0520)
```

**The gate is still real at the corrected stamp** — quiet acceptance would be worthless.
With `- verb:dbus` changed to `- notaclass:dbus` in a plugin candy:

```
charly: error: command "validate": 2 validation errors:
  candy "plugin-dbus": CUE schema: .../candy/plugin-dbus/charly.yml:
  candy "plugin-dbus": 2 errors in empty disjunction:
```

So the repo still gets the gate the previous PR was for, and its `candy` workflow goes green
again.
