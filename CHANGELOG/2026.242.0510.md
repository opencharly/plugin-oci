# 2026.242.0510 — fix: add a root charly.yml so the candy CI gate is real

## Summary

Makes this repo's candy CI gate actually gate something.

Without a root `charly.yml` a plugin repo is **project-less**: charly scans **no candies at
all**, so the stock `charly box validate` step in `deploy.yml` exits 0 on any manifest —
including one with a malformed `plugin.providers` entry. The step has been asserting
nothing.

A four-line `discover:` block is the whole fix. The candy becomes scannable, the CUE schema
gate applies, and the **stock** step starts working — no workflow change needed. The file
declares no entities of its own; it only tells charly where to look.

Refs opencharly/charly#459.

## How tested

The mechanism and the fix were established on `opencharly/plugin-punktfunk`
(opencharly/plugin-punktfunk#4), with a plain layer candy to isolate it — `box list candies`
filters plugin candies out of its own output, so a plugin candy alone cannot show this:

```
# candy/plainlayer/charly.yml exists, no root charly.yml
$ charly box list candies         # (nothing — not scanned at all)
$ charly box validate             # exit 0 even with a bogus field in the candy

# with the 4-line root charly.yml
$ charly box list candies
plainlayer [testing]
$ charly box validate
... notafield: field not allowed
```

And on a real plugin candy, before/after, same repo and command:

```
# `- verb:punktfunk` changed to `- notaclass:punktfunk`
# BEFORE: exit 0
# AFTER:
charly: error: command "validate": 2 validation errors:
  plugin.providers.0: invalid value "notaclass:punktfunk"
    (out of bound =~"^(kind|deploy|verb|step|build|builder|command|loader|refs|agent-runtime|terminal):...")
```

**Consumers are unaffected**, which is the real risk of adding a root manifest — a consuming
project might resolve the candy twice (once via its pinned subpath ref, once via the new
`discover:`). Tested by injecting the manifest into the *fetched* checkout that
`opencharly/distro-cachyos` resolves for a pinned plugin candy, then validating that project
both ways: identical result, exit 0 either way.

**This repo's own gate is the acceptance:** the `build` check on this PR runs
`charly box validate` at this repo root against the pinned charly. It now scans this repo's
candy, so a green check here is the first time that step has meant anything for this repo.
